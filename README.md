# 帯付けくん

マイソク（不動産チラシPDF）の **他社帯** を自動で白塗りし、登録した **自社帯** に差し替えるWebツール。社内数人での利用を想定。

**公開URL（Hugging Face Spaces）**: https://huggingface.co/spaces/kq1kq1/obiduke-kun
（Publicなら誰でもブラウザから利用可。HFアカウント不要）

## 何をするか

1. PDFをアップロード（複数可・ドラッグ＆ドロップ対応／アップロード進捗バー表示）
2. 各ページから他社の会社情報帯・ロゴを自動検出して白塗り
3. その位置に自社帯を貼り付け
4. レビュー画面で確認・修正し、PDFとしてダウンロード
   - 処理中は **完了までの推定残り時間（ETA）** を表示
   - レビュー画面でページを **ドラッグして並べ替え**（出力PDFの順序に反映）
   - 各ページの帯・白塗りを **枠の直接編集** で修正できる（後述）
   - 横向きで登録された図面を **90度単位で回転** できる（後述）
5. 確認・修正した内容が **学習データとして貯まり、再学習で精度が上がる**（後述）

### レビュー画面の枠エディタ

カードをクリックすると、帯付け前の元画像の上に検出枠が表示される。

- **橙＝帯（自社帯に差し替え）/ 赤＝白塗り / 青＝案内図**
- 枠を **ドラッグで移動**、選択中に出る青ハンドルで **サイズ変更**、**×で削除**
- 「＋帯」「＋案内図」「＋白塗り」で枠を **追加**（帯は全幅・縦のみ調整、それ以外は2D自由）
- 選択中の枠は **種類を後から変更** できる（誤って案内図と判定されたものを白塗りに直す等）
- 「適用して貼り直す」で元画像から再構成（誤検出の削除・ズレ修正・取りこぼし追加が1画面で完結）

### 「白塗り」と学習クラスの関係

使う人が選ぶのは **帯 / 案内図 / 白塗り** の3種類だけ。迷う余地を減らすため、
ロゴ・QRコード・電話番号などは全部「白塗り」でまとめてよい。

内部では4種類を持っている。

| 内部のクラス | 何か | 学習ラベル |
|---|---|---|
| `band` | 他社の会社情報帯 | 0 = band |
| `map` | 案内図 | 2 = map |
| `logo` | モデルが「他社ロゴ」として検出したもの | 1 = logo |
| `wo` | 人が「白塗り」ボタンで足した枠 | **1 = logo**（同じ扱い） |

`wo` を `logo` に寄せているのは、アプリでの logo の実用上の意味が
**「白塗りすべき局所領域」**であり、人が白塗りした場所もまさにそれだから。

ただし記録の `boxes` には `cls="wo"` が**そのまま残る**ので、あとから
「人が足した分は学習に使わない」と方針を変えることもできる（`label` 行を
`boxes` から作り直せばよい）。判断を先送りできる形にしてある。

**リスクと見張り方**: `logo` の定義が「他社ロゴ」から「隠したい局所領域」に広がるため、
ロゴの誤検出が増える可能性がある。ただし
1. ロゴの誤検出は「余分な白い四角を人が消す」だけで、帯の見逃しよりずっと軽い
2. 凍結検証セットが logo の再現率・適合率を測るので、**悪化したら数字に出て採用されない**

（現在の基準: logo 再現率 0.857 / 適合率 0.857）

### ページの回転

販売図面には縦長のものが横向きで登録されていることがあり、そのままだと帯を検出できない。
エディタの「↺ 左90°」「↻ 右90°」で直せる。

- **回すと枠は引き直しになる。** 帯は「常に全幅」の規約なので、回すと縦帯になって規約が壊れる。
  座標を回転させる計算はできるが規約が壊れる以上やる価値がないため、消して置き直す。
- 回転後に **もう一度だけ検出して推奨位置を出す**（自動では貼らない。人が確認して「適用して貼り直す」）
- 回転した時点で出力PDFの向きは直る。枠を貼らなくても向きだけ直して出せる。
- 回転すると「記録済み」の印が外れるので、そのページは改めて記録の対象になる。

元画像 `_orig` は絶対に書き換えず、累積角度を meta に持って毎回そこから作り直す。
回すたびに上書きするとJPEGの再エンコードが重なって画質が落ちていくため
（実測: 4回転して1周させると画素差が平均3.05・最大171）。

## 検出のしくみ（YOLO物体検出）

`detect.py` が学習済みYOLOモデル（`best.pt`）で検出する。マイソクの画像フォーマットがバラバラでも見た目を学習しているため頑健。

- **band（他社の会社情報帯）**: 白塗りして自社帯に差し替え（全幅に広げて確実に隠す）
- **logo（他社ロゴ）**: 白塗りのみ
- **map（案内図）**: アップロード時のチェックで「案内図も白塗りする」を選んだ場合のみ白塗り（区画図は対象外）
- 取りこぼし・誤検出はレビュー画面の枠エディタで手動修正。

### 座標の持ち方（ラベル用と白塗り用を分ける）

矩形には2つの役割があり、混ぜると再学習が壊れる。

| | 役割 | 求められること |
|---|---|---|
| **保存する矩形** | 「他社帯はここにある」という事実＝**学習ラベル** | ぴったり |
| **貼る矩形** | 白塗りする範囲 | 取りこぼさないよう少し大きめ |

そのため `label_rect()` が保存する座標を作り、`paste_rect()` が**貼る瞬間だけ**上下左右に
パディングを足す（band は 高さ×0.6%、logo/map/other は 高さ×0.4%）。
パディングを保存側に足すと「帯は実際より少し大きい」とモデルが覚えてしまう。

**band のラベルは常に全幅（`x_center=0.5, width=1.0`）で統一する。** 他社帯は実際ほぼ常に
全幅の横帯で、白塗りも必ず全幅に広げるため、エディタで人が直す枠も全幅になる。
検出枠と手修正枠でx方向の規約が混ざるとYOLOの枠回帰が濁るので、全幅に揃えてある。

Roboflowで「帯にぴったり」付けた既存ラベルがある場合は、Export後に一度だけ揃える:

```powershell
python tools/relabel_band_fullwidth.py <YOLOv8形式Exportのルート> --dry-run   # 件数だけ確認
python tools/relabel_band_fullwidth.py <YOLOv8形式Exportのルート>             # 書き換え
```

band行の `x_center` を 0.5、`width` を 1.0 に書き換えるだけ（y方向とlogo/mapは触らない）。
Roboflow上で枠を描き直す必要はない。

### 推論の高速化（OpenVINO）

Intel CPU（HF Spaces含む）では PyTorch より OpenVINO の方が速いため、`best.pt` を
OpenVINO形式に変換した `best_openvino_model/` を優先して使う（無ければ `best.pt` に
フォールバック）。起動時にウォームアップ（モデルのコンパイル）を済ませて1枚目から速くする。

## 手修正を学習データとして貯める（使うほど精度が上がる）

人が確認・修正した内容は、そのままYOLOの正解データになる。これを貯めて定期的に再学習すると、
苦手なフォーマットが減っていく。

### 貯まるタイミング

**使う人は何も操作しなくてよい。** 普段どおり処理してダウンロードするだけで貯まる。

| きっかけ | 記録される内容 |
|---|---|
| 枠を直して「適用して貼り直す」 | 直した後の枠（`edited: true`）＝**失敗例** |
| ダウンロード（直さなかったページから抽選） | 検出結果をそのまま（`edited: false`）＝**成功例** |

抽選の割合は `TRAINING_SAMPLE_RATE`（既定 **20%**）。

**なぜ成功例も貯めるのか**: 直したページばかり貯めると「モデルが間違える場面」だけの
データになり、**正しく当たっている場面を忘れる**方向に学習が進む（誤検出が増える）。

**なぜ全部ではなく一部なのか**: 全部入れると簡単な成功例で埋まって、**直すべき事例の
影響が薄まる**。修正が全体の1〜2割なので、残りから2割抜くと両者がだいたい同数になる。
`tools/fetch_training_data.py` が「人が修正 / 確認のみ」の内訳を出すので、偏っていたら調整する。

**なぜダウンロードの瞬間なのか**: ダウンロード＝この出力で良いと人が判断した合図だから。
レビュー中に記録すると、あとで削除・修正されたページまで残る。出力から削除したページは
記録されない。抽選はジョブごとに1回だけなので、何度ダウンロードしても割合は上がらない。

**人にチェックを押させないのはなぜか**: 以前は ✓ ボタンで明示的に確認させていたが、
やめた。押すのが手間だと誰も押さず、結果として**失敗例しか貯まらない**（いちばん避けたい
状態）。「見て、直さずにダウンロードした」も十分な合図として扱う。

枠が0個のページも記録される。「ここには帯もロゴも無い」という例は、
**誤検出（関係ない場所への白塗り）を減らすのに効く教師データ**になる。

案内図のチェックがオフのときも、検出された案内図は白塗りせずに**ラベルとしては残す**
（捨てると「ここに案内図は無い」と教えることになり、案内図の検出力が落ちる）。

### 貯まる場所

Spacesのディスクは再起動で消えるため、private な **Hugging Face Dataset リポジトリ**に送る。
無料アカウントでも **private 100GB** の無料枠があり、1ページ約250KBなので数千ページでも余裕。

```
<Datasetリポジトリ>/data/
  images/<SHA先頭2文字>/<SHA256>.jpg   帯を貼る前の元画像（内容ハッシュ名なので重複しない）
  records/records_<uuid>.jsonl         1行1ページの記録（追記のみ）
```

同じページを何度直しても画像は1枚のまま、JSONLに行が増える。学習時は**画像ごとに最後の行**を
採用するので、最新の修正が勝つ（間違って記録されても、枠を直して貼り直せば上書きできる）。

### 設定（HF Spaces）

Space の Settings > Variables and secrets に登録する。**未設定なら機能は自動でOFF**になり、
何も記録・送信されない。

| 種別 | 名前 | 値 |
|---|---|---|
| Secret | `HF_TOKEN` | 書き込み権限のあるHFトークン |
| Variable | `TRAINING_DATA_REPO` | 例 `kq1kq1/obiduke-training-data` |
| Variable | `TRAINING_DATA_EVERY` | 保険タイマーの間隔（分）。省略時 30 |
| Variable | `TRAINING_SAMPLE_RATE` | 成功例を抜き取る割合。省略時 0.2（20%） |

> ⚠️ **マイソクには他社担当者名・連絡先・物件情報が載る。** リポジトリは起動時に
> `private=True` で作られる。**絶対に公開に切り替えないこと。**

### 送信のタイミング

| きっかけ | 動き |
|---|---|
| **PDFをダウンロードした** | 成功例を抽選して記録し、**その場で即送信** |
| タイマー（既定30分） | 取りこぼしの保険。「確認したがダウンロードせず閉じた」ときだけ効く |
| 新しいデータが無いとき | 何もしない（空コミットは捨てられる）。使わない日は通信も起きない |

ダウンロードで送り切るので、**失われるぶんは通常ほぼ無い**。

タイマーを短くするとコミットが増えてHub上の動作が重くなる（公式に数千コミットで劣化するとある）。
1日10回×確認10分の使い方なら、2分間隔だと年4000コミットに達するので30分にしてある。
それでも増えてきたら、次項の `--squash` で履歴を畳める。

### 貯まったデータの確認・取り出し

```powershell
$env:HF_TOKEN = "hf_xxx"
python tools/fetch_training_data.py kq1kq1/obiduke-training-data --out collected
```

`collected/images/` と `collected/labels/` がYOLO形式で出力され、内訳（ページ数・クラス別の枠の数・
枠0個のページ数）が表示される。データがまともに貯まっているかはこれで確認する。

`--squash` を付けると、取り出したあとにリポジトリの履歴を1コミットに畳む。
**データ本体は消えず、履歴だけが消える**（追記専用のデータ置き場なので履歴に価値はない）。
再学習のたびに付けておけばコミット数は永久に問題にならない。取り消せないので、
1件も取り出せなかった場合は畳まずに中止する。誰かが使っている最中は避ける。

```powershell
python tools/fetch_training_data.py kq1kq1/obiduke-training-data --out collected --squash
```

## 再学習でモデルが悪化しないようにする

新しいモデルが本当に良くなったかを判定できないまま差し替えるのが、精度を下げる一番のルート。
そのための物差しを固定してある。

### 凍結検証セット

Roboflowはバージョンを作り直すたびに valid/test を切り直すので、そのままでは物差しが毎回変わる。
現モデルが学習に使っていない **29枚（v3の valid 19 + test 10）** を凍結してある。

- 画像とラベル: `datasets/frozen_val/`（Git管理外）
- 定義: `eval/frozen_val_manifest.json`（**Git管理。これが正**）
- **この29枚は学習に絶対に使わないこと。** 使うと基準スコアが甘く出て比較にならない。

作り直すと過去のスコアと比較できなくなるため、`tools/freeze_val_set.py` は既に凍結済みなら
何もしない（どうしても必要なときだけ `--force`）。

### 採点

```powershell
python tools/eval_model.py best.pt --sweep
python tools/eval_model.py 新しいbest.pt --save eval/candidate.json
```

一般的な mAP ではなく、**アプリが実際に困っている2つ**を直接測る。

- **検出漏れ（再現率）** … 赤い「未検出」になって手作業が増える
- **誤検出（適合率）** … 関係ない場所が白塗りされる

band は **y方向だけのIoU** で判定する。`paste_rect` が必ず全幅に広げるので x座標は捨てられており、
mAPだと実務では関係ない x方向のズレで良し悪しを判断してしまうため。

### 現モデル（best.pt）の基準スコア

`conf=0.30 / imgsz=640`（アプリと同条件）、29枚、**縦横比を保った元解像度の画像**で測定。

| クラス | 再現率 | 実害誤検出 | 重複 | 見逃し |
|---|---|---|---|---|
| band | 0.893 | 4 | 7 | 3 |
| logo | **0.571** | 1 | 2 | 3 |
| map | 0.870 | 1 | 0 | 3 |

帯を1つも出せなかったページ: 2 / 29（6.9%）

**新しいモデルはこれを上回っていること。下回ったら採用しない。**

#### 誤検出を2種類に分けている理由

| | 内容 | 実害 |
|---|---|---|
| **実害誤検出** | 関係ない場所を白塗りしてしまう | **大きい**。人が気づかないと事故になる |
| **重複** | 同じ対象を二重に検出 | **無い**。帯は必ず全幅に広げて貼るので結果は同じ |

分けずに数えると、無害な重複のせいで適合率が悪く見えて判断を誤る。
実際、分ける前は「確信度を 0.30→0.40 にすれば誤検出が半減する」と見えていたが、
分けたら**減っていたのは重複だけで、実害のある誤検出は変わらなかった**。

#### 帯が無い図面の扱い

**「帯を出せなかったページ」は、正解に帯があるページだけを数えている**
（`tools/eval_model.py` の該当箇所）。帯が最初から無い図面で帯を出さないのは正解なので、
減点されない。逆に帯が無いページで帯を出したら実害誤検出として数える。

凍結検証セット29枚の内訳: 帯があるページ **28枚** / 帯が無いページ **1枚**。

### 分かっていること

- **画像を潰していた影響は実際に大きかった。** 同じモデル・同じ29枚で前処理だけ変えて測ると
  **logo の再現率が 0.857 → 0.571** に落ちた。潰した画像で測ると成績が良く見えていただけで、
  本番で起きていたのはこちら。小さい対象（ロゴ）ほど潰しの影響を受ける。
  **v4（リサイズ無し）で学習し直すのが、今いちばん効きそうな一手。**
- **案B（band全幅）への規約変更は精度に影響しない。** 両規約で採点して数値が完全に一致した
- **確信度は 0.30 のままでよい。** 実害のある誤検出だけで見ると 0.30〜0.40 は同じ（4件）、
  0.50 で1件減るだけで、29枚では誤差の範囲
- **推論解像度 800 が有望（未確定）。** 640→800 で band再現 0.893→0.929、logo再現 0.571→0.714、
  帯を出せないページ 2→1 と改善する一方、処理時間は約1.5倍。960以上は崩れる。
  ただし差は1件ぶんなので、v4で学習し直した後にもう一度測ってから決める

### 検証セットが小さいことについて

29枚しかないので、小さな差は判定できない（誤検出2件の違いは誤差の範囲）。
蓄積データが貯まったら、その一部を検証用に取り分けて凍結セットを広げること。
**取り分けた分は学習に使わない。**

### ⚠️ 学習画像が潰れている問題（次の再学習の前に直すこと）

Roboflowの v3 は **Stretch to 640×640** で書き出されていて、縦長のマイソクが正方形に
押し潰された状態で学習されている。一方、推論時のultralyticsは縦横比を保ったまま
余白を足す（letterbox）。**潰れた絵で学習して、潰れていない絵を見せている。**

アプリが貯める蓄積データは元の縦横比のままなので、このまま混ぜると
「潰れた画像」と「潰れていない画像」が同じ学習データに同居してさらに濁る。

**直し方**（次の再学習の前に一度だけ）:

1. Roboflowで **Create New Version**
2. Preprocessing の **Resize を削除**（または「Fit within」にする）。ultralyticsが
   学習時にも推論時と同じletterboxをかけるので、Roboflow側でリサイズしないのが一番揃う
3. YOLOv8形式でExport → `datasets/roboflow/v4/` に展開
4. **凍結検証セットを作り直す**:
   ```powershell
   python tools/freeze_val_set.py datasets/roboflow/v4 --force
   python tools/eval_model.py best.pt --save eval/baseline_best_pt.json
   ```
   `--force` は物差しを変える操作なので普段は使わない。**蓄積データが貯まる前の今だけ**
   やっておく。後からやると過去のスコアと比較できなくなる。

## 再学習パイプライン

### 一度だけ: 土台データをHubに置く

```powershell
$env:HF_TOKEN = "hf_xxx"
python tools/upload_base_dataset.py kq1kq1/obiduke-training-data --dry-run   # 中身の確認
python tools/upload_base_dataset.py kq1kq1/obiduke-training-data
```

Roboflowの学習分（bandを全幅に統一）と凍結検証セットを `base/` に置く。
以後の再学習は **HF_TOKEN だけで学習データが全部そろう**。
凍結検証セットが自分のPCにしか無い状態も解消される（消えると比較の物差しを失うため）。

### 毎回: 再学習して判定する

Colab（無料GPU）で:

```python
!git clone https://github.com/kq1kq1/obiduke-kun && cd obiduke-kun
!pip install -q ultralytics huggingface_hub
import os; os.environ['HF_TOKEN'] = 'hf_xxx'
!python tools/train_new_model.py kq1kq1/obiduke-training-data --epochs 100
```

やること:

1. Hubから土台データと蓄積データを落とす
2. 学習 = 土台の学習分 ＋ 蓄積データ / 検証 = 凍結セットだけ、で組む
3. **検証画像が学習に混ざっていないか確認**（混ざったら止まる）
4. 今の `best.pt` から続きを学習（ゼロからより速く、覚えたことも残る）
5. 凍結検証セットで採点して基準スコアと比較

判定は3つ。

| 判定 | 条件 |
|---|---|
| **採用しない** | 帯の再現率が下がった、または帯を出せないページが増えた |
| **採用してよい** | 悪化がなく、どれかが改善した |
| **判断が必要** | 悪化はないが改善もない → **見送るのが安全** |

帯の見逃しは赤い「未検出」になって手作業が増えるので、**誤検出がどれだけ減っても
見逃しが増えたら採用しない**。

### 採用するとき

```powershell
# 1. training_run/train/weights/best.pt を best.pt に上書き
python -c "from ultralytics import YOLO; YOLO('best.pt').export(format='openvino', imgsz=640)"
python tools/eval_model.py best.pt                              # 上書き後に再確認
python tools/eval_model.py best.pt --save eval/baseline_best_pt.json  # 基準を更新
python tools/selfcheck_rotation.py                              # デプロイ前チェック
git add -A; git commit -m "モデル更新"; .
edeploy_hf.ps1
```

**基準スコアの更新を忘れないこと。** 次の再学習はこれと比べる。

### モデルの再学習（精度を上げたいとき）

苦手なフォーマット（検出漏れ・新しい帯/ロゴ/案内図）が出たら、画像を足して再学習すれば改善する。
**毎回「今回の増分だけ」ではなく、累積した全データで学習し直す**こと（増分だけだと以前できていた
ことが劣化する＝忘却が起きる）。

1. `python tools/fetch_training_data.py <Datasetリポジトリ> --out collected` で貯まった分を取り出す
2. 既存のRoboflowデータをYOLOv8形式でExport（band規約が未統一なら `tools/relabel_band_fullwidth.py` で揃える）
3. 1と2を混ぜて Google Colab（無料GPU）で `ultralytics` で学習
4. **旧モデルと新モデルのmAPを比較**し、良くなっていることを確認してから採用する
5. 出来た `best.pt` をプロジェクト直下に上書き
6. **OpenVINO形式を作り直す**:
   ```powershell
   python -c "from ultralytics import YOLO; YOLO('best.pt').export(format='openvino', imgsz=640)"
   ```
7. `best.pt` と `best_openvino_model/` をコミットして再デプロイ（後述の「再デプロイ手順」）

苦手なPDFを手で足したいときは、`samples/` に入れて `python export_images.py` で
`training_images/` にPNG化し、Roboflowでラベル付けする（従来どおり）。

## 使い方

1. `/bands`（自社帯の管理）で全幅の横帯画像（PNG/JPG）を登録
   - 複数登録できる。「デフォルトにする」で、トップページで最初に選ばれる帯を変更できる（`own_bands_default.txt` に記録）
2. トップページで自社帯を選び、PDFをアップロードして「処理開始」
3. 処理完了後、レビュー画面で各ページを確認
   - 検出漏れページは赤く表示される。カードをクリックして枠エディタで帯・白塗りを追加／修正
   - 横向きで登録された図面は、カードを開いて「↺ 左90°」「↻ 右90°」で直す
4. 「ダウンロード」でPDFを取得

### 自社帯について

- 対応形式は **PNG / JPG**（透過させたいときはPNG）。ファイル名は **英数字（アンダースコア区切り）推奨**（日本語名は文字化けの素）。
- 画面の「アップロード」から足した帯は **再起動で消える**（HFのファイルシステムが揮発性のため）。**恒久的に残す帯は `own_bands/` に置いてコミット→再デプロイ**する。
- 同時アクセス時の安全性: ジョブはUUIDで分離され、共有モデルの推論はロックで直列化しているため、社内数人が同時に処理しても結果は混ざらない。

## デプロイ（Hugging Face Spaces）

- Space: https://huggingface.co/spaces/kq1kq1/obiduke-kun
- SDK: **Docker**（`Dockerfile` 同梱、ポート7860）
- 進捗をメモリ上で管理するため **gunicorn worker は1つ固定**（複数workerだと進捗共有が壊れる）。並行アクセスはthreadsで処理。
- HFは**バイナリをGit LFSで管理する必要がある**（`best.pt` / `best_openvino_model/*.bin` / `own_bands/*.png` / `*.jpg`）。
- 注意: Spacesのファイルシステムは再起動で初期化されるため、画面から登録した自社帯は再起動後に消える。恒久的に増やすなら `own_bands/` に置いてコミット→再デプロイする。
- 学習データの蓄積を使う場合は Settings > Variables and secrets に `HF_TOKEN` / `TRAINING_DATA_REPO` を登録する（上の「手修正を学習データとして貯める」を参照）。ダウンロード時に送信し切るので、レビュー→ダウンロードまで済んでいれば再デプロイしても失われない。
- 再デプロイは `main` を前提にしたスクリプト（`git push origin main` と `git checkout main` をする）。**ワークツリーからは実行できない**ので、変更を `main` にマージしてから本体フォルダで実行する。

- 画像・モデルは **GitHub にも入っている**（GitHubはLFSなしで100MBまでのバイナリを持てる）。GitHubがフル履歴・バックアップ、HFが公開・実行先。

### 再デプロイ手順

**いちばん簡単な方法**: まず変更を main にコミットしてから、付属スクリプトを実行する。

```powershell
git add -A
git commit -m "変更内容"
.\redeploy_hf.ps1   # GitHub push → HFへLFS付き単一コミットをforce push まで自動
```

実行するとHFの **Write トークン** を聞かれるので貼る（画面に表示されず保存もされない）。
トークンは https://huggingface.co/settings/tokens で発行（使い終わったら失効可）。
